## Item-by-item

### 1. Critical — unbounded reference/definition accumulation. **ADDRESSED**

`src/parser.ts:201-202`:

```ts
const nextIsScheduleOrCommentRef: boolean =
    nextLine.startsWith("<!--SR:") ||
    /^\[\^sr-[0-9a-f]{6}\]( <!--SR:|$)/.test(nextLine);
```

Exactly the mandated regex, with the rename and a comment that names the death mode so nobody
"simplifies" the `$` away.

Verified by reverting the regex to `/^\[\^sr-[0-9a-f]{6}\] <!--SR:/` and re-running the suite:
**2 failures, and precisely the right 2** —

```
● card comment convergence › cardCommentOnSameLine: false › an inline card with no schedule, three comment flushes
● card comment convergence › cardCommentOnSameLine: false › a card with an Obsidian block id with no schedule, three comment flushes
```

No CRLF hole. I checked specifically, because `$` with no `m` flag would not match a line ending
in `\r`: `parse()` does `text.replaceAll("\r\n", "\n").split("\n")` at line 101 *before* the
lookahead runs, so the alternative is safe on CRLF notes. I also ran the whole convergence block
against a CRLF version of every note shape — 22/22 pass — and confirmed end-to-end CRLF
preservation through `findAndReplace` and `upsertFootnoteDefinition`.

### 2. Important — orphaned reference after a write miss. **ADDRESSED**

`notes-data-store.ts:115-131`: snapshot before `resolveCardComment`, restore on the early return.
Restoring rather than nulling is the right call, and the second committed test pins it
(a card that already had a real definition keeps its label).

The rollback is sound structurally, not just locally: `resolveCardComment` is called from
**exactly one** place in the codebase (`NotesDataStore.write`), so there is no second site that
can mint a label and fail to write it. `Question.writeQuestion` (the Edit Card path) does write
unconditionally, but it never resolves a comment — it only re-emits whatever reference is on the
question, which after the rollback is the pre-existing one. The invariant "a reference never
outlives its definition" now holds on every path.

Verified by deleting the restore line: 1 failure, `card comments › a write miss leaves no label
behind for the next write to orphan`.

### 3. Important — definition line inside a card leaves `original` non-contiguous. **ADDRESSED**

`src/parser.ts:132-143`: the definition line now flushes the accumulating card with
`lastLineNo = i - 1` and resets `cardText`/`firstLineNo`, exactly as the blank-line branch does.

Verified by reverting to the old `continue`-only skip. One test fails
(`Test footnote definitions are skipped entirely`) — and it fails on the first of its several
new `expect`s, which is why the count is 1 rather than 3. The later assertions *are* real: with
the fix reverted I measured, directly,

```
"How do you write a footnote?\n?\n[^1]: the text\nand more answer\n"
  -> [MultiLineBasic, "How do you write a footnote?\n?\nand more answer", 0, 3]  note.includes(text) === false
"F\n?\nA line\n[^1]: the text\nand more answer\n"
  -> [MultiLineBasic, "F\n?\nA line\nand more answer", 0, 4]                     note.includes(text) === false
```

so the committed `expect(noteText).toContain(contiguous[0][1])` genuinely covers the regression.
On `11d95ac` both shapes are contiguous slices.

### 4. Important — two identical cards, comment on the wrong card. **ADDRESSED**

`MultiLineTextFinder.countMatches` (additive), `Question.isTextAmbiguousWithinNote`,
`Question.discardPendingCardComment`, and the guard at `notes-data-store.ts:104-110`.

Verified by short-circuiting the guard to `false`: 2 failures, the refusal test and the
three-flush byte-identity test.

### 5. Important ×2 (documentation) — re-indentation, blockquote guard. **ADDRESSED**

Both written down in three places each, and written down *well* — the spec's new **Limitations**
section leads with the actionable rule ("leave a blank line before anything you add under an
`sr-` footnote"), shows the before/after, and states plainly that nothing is deleted and the
damage is the flattening of nesting to one 6-space level. The ledger's wrong "loses the glued

correctly. This is the right resolution: narrowing `findDefinitionRange` would narrow markdown's
own lazy-continuation rule and risks losing a line, which is the failure class the branch exists
to exclude.

### 6. `lastLineNum` inflation. **ADDRESSED**

Falls out of item 3. `tests/unit/parser.test.ts` previously *encoded* the inflated value

No consumer is harmed: `lastLineNum` is read only through `isQuestionLineNum` at

## The eight scrutiny questions

### Is the convergence test actually strong?

**Yes, and it was not weakened.** `git diff c15a826 11d95ac --
tests/unit/scheduling/flashcard-review-sequencer.test.ts` is **+101 / −0**: a single hunk of pure
addition (the I2 and I4 tests). The convergence block committed RED at `c15a826` is byte-identical
at `11d95ac`. There is no relaxation to find.

What it actually asserts, per case:

- `skeleton(final) === skeleton(original)` — byte equality of everything the feature may not
  touch: the `sr-` definition block cut away (together with the blank lines introducing it),
  reference tokens removed with their one adjacent space-or-newline, `<!--SR:…-->` masked.
- exactly one reference on the card and exactly one definition in the note;
- all three entries, in order, in that one definition.

Three cycles, five card shapes (inline, multi-line, cloze, code-fence-ending, Obsidian block id),
two drivers (three rated `processReview`s, and three `flushPendingCardComment`es on an unscheduled
card), under **both** `cardCommentOnSameLine` values — 20 cases, plus the round trip per setting.
Every note also carries a `# Heading`, prose after the card, the user's own `[^1]` footnote *with
an indented continuation*, and a named `[^note]` footnote, so spec item 6 is re-checked 22 times
rather than once.

Two things I checked rather than assumed:

- **The skeleton cannot hide a misplacement.** It cuts at the *first* `sr-` definition line. If
  the plugin ever wrote the definition block above the user's footnotes, `skeleton(final)` would
  lose the prose and the user's footnotes while `skeleton(original)` kept them — the comparison
  fails loudly. The relaxation only ever runs in the safe direction.
- **The learned baseline is a methodological strength, with one stated cost.** Using the plugin's
  own post-first-review output as `original` removes a class of false red (a card ending in
  ```` ``` ```` does *not* take `endsWithCodeBlock()` here, so its schedule lands on the fence
  line). The cost, which the implementer names honestly, is that a defect in the *first*
  schedule write is invisible to the rated-review cases. Note the flush cases do not have this
  cost: there `original` is the true input note.

Genuine relaxations, both small and both declared: trailing newlines are normalised
(`\n+$` → ""), so the known one-time trailing-blank-line collapse is excluded; and `\r\n` is
normalised, so a CRLF→LF conversion would not be caught by this assertion (I checked that
separately and separately — see item 1 — and CRLF is preserved).

**Shape coverage I added myself.** The spec's item 2 enumerates six shapes; the convergence block
runs five, omitting **single-line-reversed** (`::::`). I ran the entire block, unmodified except
for the shape list, over single-line-reversed, multi-line-reversed (`??`), a card ending in a
`$$` math block, a card nested in a list, and an inline control: **22/22 pass** under both
settings. I then re-ran it with YAML frontmatter, with no trailing newline, and with CRLF
throughout: 22/22 each. So the gap is coverage, not behaviour. (See Minor 4.)

### Was the reachable path really `flushPendingCardComment`, and does the fix cover every exit?

**Both confirmed.** The two tests that go red when the regex is reverted are the two
`… with no schedule, three comment flushes` cases; every `processReview` case passes either way.
The bug needs `hasSchedule === false` at `formatForNote` time, and `processReview` always gives
the card a schedule first — so the only way in is "type a comment, then leave without rating",
which is how a comment gets written on a brand-new card.

Exits, traced in `content-manager.tsx`: rate (`_processReview` → `processReview`), skip
(`_skipCurrentCard`:487-488), back-to-deck (`_showDecksList`:188-189), close (`close`:135-136),
Edit Card (:405-406, flushed *before* the edit). All five call `_stageCardComment()` and then
either `flushPendingCardComment()` or `processReview`, and **all of them funnel into
`NotesDataStore.write`** — the single function that holds both the ambiguity guard and the label
rollback. Delete Card (`_deleteCurrentCard`:349-352) deliberately clears the box without
flushing, with a comment explaining why (the definition would be orphaned a moment later); the
spec now says so too. There is no sixth write path.

### `countMatches` on a shared utility

`git diff cb4a596~1 11d95ac -- src/utils/strings.ts` — the **entire branch's** change to
`strings.ts` is the addition of `countMatches`. `find` and `findAndReplace` are untouched,
character for character, and nothing else's behaviour changes.

It faithfully mirrors `find`'s comparison, *including* `find`'s own reset deficiency. I probed
this directly:

```
source ["A","A","A","B"], search ["A","A","B"]  ->  countMatches 0, find null
source ["A","A","B"],     search ["A","B"]      ->  countMatches 0, find null
source two copies of "Q1::A1"                   ->  countMatches 2
"Q1::A1" inside "Q1::A1 <!--SR:x-->"            ->  countMatches 0  (whole trimmed line)
```

The mirroring is what makes the guard safe: wherever `countMatches` under-counts, `find` also
misses, so the write is suppressed anyway by the `lastUpdateFoundOriginal` branch. It can never
*over*-refuse relative to what `findAndReplace` would actually do. The whole-line comparison is
also the right choice over `indexOf` — a substring count would fire whenever one card's text is a
prefix of another's line, silently eating a comment on an innocent card, and there is a committed
test for exactly that.

**Is refusing-but-still-writing coherent?** Yes, and it does not reintroduce finding 2. The
discard happens *before* `resolveCardComment`, so no label is ever minted on the refused path —
there is no reference to orphan. The committed test asserts `expect(fileText).not.toContain("[^sr-")`
and the unscheduled three-flush test asserts the file is byte-identical to its input after three
comments. The only way an ambiguous card can carry a reference at all is the hand-edit
"two cards sharing one label" case, which the spec already lists as degenerate. The schedule
still persisting is right: the copies are byte-identical, so their schedules are interchangeable,
and first-match-wins there is pre-existing upstream behaviour this branch has no business
changing.

### The empty-answer behaviour change

I reproduced the full lifecycle. For `#flashcards\nHow do you write a footnote?\n?\n[^1]: the
text\nand more answer\n`:

```
card enters the deck:  front="How do you write a footnote?"  back=""  nCards=1
after one rated review with a comment:
    #flashcards
    How do you write a footnote?
    ? [^sr-5b6339] <!--SR:!2023-09-06,0,230-->
    [^1]: the text
    and more answer

    [^sr-5b6339]: - *2023-09-06:* a thought on an empty-answer card
re-parse: hasCurrentCard === false
```

So: **yes**, an empty answer reaches the scheduler, reaches the renderer, and reaches a write.
What then happens is that the schedule lands on the `?` separator line, the line no longer trims
to `?`, and the card silently leaves the deck on the next parse.

**And that is byte-for-byte what already happens today** for the blank-line equivalent
`#flashcards\nHow do you write a footnote?\n?\n\nand more answer\n` — I ran it side by side:
same empty back, same `? <!--SR:…-->`, same `hasCurrentCard === false` on re-parse. The
implementer's "safe and consistent with how a blank line behaves" is therefore literally true,
not a rationalisation.

Judged: **acceptable.** The user's `[^1]: the text` and `and more answer` survive byte-for-byte.
The trade is "card stays in the queue forever and its schedule silently never persists" (the I3
bug) for "card writes once and then silently leaves the deck". The second is strictly less bad —
nothing is destroyed, and a card vanishing is at least noticeable — and it is a shape with 0
occurrences in the vault, confirmed independently below. It is in the spec's Limitations. One
consequence worth adding there: the comment definition the user typed is left at EOF pointing at
a card that no longer parses (Minor 3).

### Is the silent duplicate-card refusal acceptable?

**For this fork today, yes** — with one correction to the premise, and one nit.

The premise checks out: no real card in the vault is ambiguous. My own scan found 2 ambiguous
parse results, and both are the same line, `**Status:** {{Trivial by homogeneity}}`, repeated in
`<a note>.md` — a note carrying **none**
of the vault's ten flashcard tags, so `NoteQuestionParser` never builds them into a deck. They
are not cards. (They are, however, two identical cloze lines sitting in the vault: add a
`#flashcards` tag to that note and the guard starts firing. One tag away, not zero.)

A silent refusal with 0 affected cards, on a single-user fork, where the alternative was planting
a visible dated entry on the wrong card permanently, is the right trade. The implementer's own
"worth doing before anyone else uses this fork" is the correct framing and should stay on the
list. See Minor 1 for the misleading-warning nit.

## New findings

**New Critical: none. New Important: none.**

### Minor 1 — the duplicate-card warning fires even when no comment was staged

`notes-data-store.ts:104-110` runs the ambiguity check unconditionally and logs *"The comment was
discarded"* whenever the card text is ambiguous, whether or not anything was staged. A user with
two identical cards would get that warning on every rated review of them, asserting a discard
that never happened. Harmless (console only, 0 vault cards), but the message is wrong in the
common case. Gating the `console.warn` on a comment actually being pending is a two-line change.

### Minor 2 — `hasChanged` is not rolled back with the reference

`setCardCommentRef` sets `hasChanged = true`; the I2 restore puts `cardCommentRef` back but
leaves `hasChanged` set. `Note.writeNoteFile` (`note.ts:46`) re-emits questions with
`hasChanged`, so a miss can leave the question marked dirty. Content-neutral, since the restored
reference re-emits identically — worth a line only for completeness.

### Minor 3 — an empty-answer card leaves its comment definition orphaned

Documented in the spec as "such a card may lose its answer side", which is accurate but stops one
step early: the card also leaves the deck on the next parse (verified above), so any
`[^sr-…]` definition written for it survives at EOF pointing at nothing. The user's text is
intact and visible; it is just unreachable from the review UI. One sentence in the Limitations
entry would close this.

### Minor 4 — the spec claims a shape the convergence test does not run

See the fourth spec correction above. Either add `#flashcards Q1:::A1` to the `shapes` array
(it passes — I ran it) or soften the wording to the five shapes actually covered. Leaving an
overstatement in the spec is the same failure mode that produced C1: a test claim nobody
re-checked.

### Not findings, recorded so they are not rediscovered

- **`useCalloutsForSchedulingComments: true` does not converge.** Running the convergence block
  under that setting fails 12/22 on trailing-whitespace drift in the plugin's own callout lines
  (`> [!sr|card-metadata] ` loses its trailing space; `>  <!--SR:…-->` loses a space). I then
  re-ran it with **no comment staged at all** and got the same 12 failures — so this is
  pre-existing upstream behaviour of the callout format, not caused by the comment feature. The
  vault's setting is `false`. The branch simply does not cover this setting, which is consistent
  with the review's earlier scope.
- **A bare own-line reference introduces one LF into a CRLF note**
  (`#flashcards Q1::A1\n[^sr-…]\r\n`). `appendCardCommentRef` emits `\n${ref}`, which
  `findAndReplace` splices verbatim. This is identical to what upstream's own
  `getHtmlCommentSeparator` already does for an own-line schedule comment, it predates this fix
  wave, and it does not accumulate (the CRLF convergence run asserts one reference and one
  definition). Cosmetic, pre-existing, upstream.
- **`convertFoldersToDecks: true` still deletes the `#flashcards` tag on write.** Pre-existing
  upstream, confirmed on the base commit by the previous review, untouched here, and the branch
  cannot be exercised under it. Not this wave's problem, but it remains a tag-deletion bug in a
  fork whose premise is not losing bytes it does not own.

## Ship / do-not-ship

**Ship — safe to install into the real vault**, at the vault's live settings
(`cardCommentOnSameLine: true`, `useCalloutsForSchedulingComments: false`,
`convertFoldersToDecks: false`).

What that rests on:

1. The parser change is a byte-for-byte no-op on all 4437 notes / 650 SR notes, verified
   independently against both `340b86a` and the pre-branch base.
2. Every card in the vault is contiguous, so none is unwritable; no card is ambiguous, so the new
   guard never fires.
3. The C1 accumulation class is closed, and the test that closes it genuinely fails without the
   fix, across both settings and both drivers.
4. A reference can no longer outlive its definition on any of the five write exits, which all
   funnel through one function.
5. No source change outside the named findings; all six deferred items untouched; `find` and
   `findAndReplace` byte-identical to pre-branch.

Before anyone other than the author uses this fork, do the two things the implementer already
flagged: surface the duplicate-card refusal as a `Notice` rather than a `console.warn`, and do
the manual Obsidian pass on multi-entry definition rendering, which is still the open gate. The
four Minors above are tidy-ups, not blockers.
